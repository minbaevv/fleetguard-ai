# FleetGuard AI — подробный план «с нуля до под ключа»

ИИ-сервис для таксопарков и проката: водитель фотографирует машину с 4 сторон до и после
смены, система находит **новые** повреждения, формирует акт осмотра, а менеджер задаёт
вопросы по данным в чате.

Цель: сильный B2B-проект, который решает реальную боль и показывает бэкенд, фронтенд,
Computer Vision и LLM в одном работающем продукте. Один разработчик, ~6 недель,
по 3–4 часа в день (оценка, а не гарантия).

---

## 0. Как работать по этому плану (с агентами)

### 0.1 Рабочий цикл на каждую задачу
1. Открой задачу из раздела 10 (там цель, шаги и критерий «готово»).
2. Дай агенту **маленькую** задачу и контекст: `AGENTS.md`, нужный раздел плана, затронутые файлы.
3. Агент пишет код **и тесты**. Ты запускаешь тесты и линтер.
4. Читаешь изменения целиком. Если не понимаешь кусок, проси объяснить. Тебе будут задавать вопросы по коду.
5. Проверяешь критерий «готово» руками (запрос в Swagger, клик в интерфейсе).
6. Коммит (`feat: ...`, `fix: ...`). Одна задача = один коммит.

### 0.2 Роли агентов
Названия ниже примерные. Подставь свои агенты из ecc, у которых похожие роли.

| Роль | Когда использовать |

## 1. Продукт

### 1.1 Одной фразой
«Фотофиксация и ИИ-сравнение состояния кузова до и после смены, чтобы споры о повреждениях
решались за минуту и с доказательствами».

### 1.2 Пользователи
- **Водитель:** быстро сфотографировать машину по подсказкам, увидеть результат.
- **Менеджер парка:** видеть новые повреждения, акты, историю по машинам и водителям, спрашивать у ассистента.
- **Админ организации:** управляет машинами и пользователями.

### 1.3 Пользовательские истории (MVP)
1. Менеджер добавляет машину (госномер, модель).
2. Водитель создаёт осмотр «до», делает 4 фото по подсказкам, получает подтверждение.
3. В конце смены водитель создаёт осмотр «после» и делает 4 фото.
4. Система показывает: список новых повреждений, обводку на фото, серьёзность.
5. Менеджер открывает акт (веб и PDF) и видит оценку стоимости.
6. Менеджер спрашивает ассистента: «какие машины пришли с новыми повреждениями за неделю?»
7. Если фото плохое (размытое, не тот ракурс), система сразу просит переснять.

### 1.4 Вне MVP (не делаем)
Мобильное приложение, интеграции с банками и страховыми, оплата, 3D, скрытые повреждения,
видео вместо фото, мультиязычность интерфейса (только русский).

### 1.5 Критерии успеха проекта
- Демо работает по публичной ссылке с телефона.
- Новое повреждение на тестовом наборе находится в большинстве случаев, ложные срабатывания считаются и показываются честно.
- Есть README, Model Card, тесты, CI, видео на 1–2 минуты.
- Проведено 10+ разговоров с представителями парков, есть цифры.

## 2. Архитектура

```
[Next.js: водитель / менеджер]
          |  HTTPS, JSON, cookie с JWT
          v
[FastAPI] ----> [PostgreSQL]
   |    \
   |     ----> [MinIO / S3: фото, PDF]
   v
[Redis] <---- [Celery worker: CV + LLM задачи]
                 |-- quality.py   проверка качества фото
                 |-- detector.py  YOLO-seg: повреждения
                 |-- compare.py   выравнивание и поиск новых
                 |-- llm/         Vision-LLM, акт, ассистент
```

### 2.1 Принятые решения и причины
| Решение | Причина |
|---|---|
| FastAPI | Быстрая разработка, автодокументация Swagger, типы через Pydantic |
| Celery + Redis | Анализ фото долгий, API не должен ждать. Статус задачи виден в БД |
| PostgreSQL | Надёжно, JSONB для полигонов, понятные миграции |
| MinIO | S3-совместимое хранилище локально, в проде легко заменить на S3 |
| Next.js + TypeScript | Хорошо для кабинета, удобно работать с камерой телефона |
| YOLO-seg (Ultralytics) | Даёт маски повреждений, простое обучение и экспорт |
| LangChain + structured output | Акт по строгой схеме, инструменты для ассистента |
| Docker Compose | Один запуск всего, понятный деплой на VPS |

### 2.2 Асинхронный поток анализа
1. `POST /inspections/{id}/finish` ставит статус `processing` и задачу в Celery.
2. Воркер проверяет качество, запускает детектор, сохраняет `damages`.
3. Если есть парный осмотр «до»: выравнивание, сопоставление, `is_new`.
4. Для спорных случаев вызывает Vision-LLM (с лимитом).
5. Статус `done` (или `failed` с причиной). Фронтенд опрашивает статус раз в 2 секунды.
6. Для пары «до/после» создаётся отчёт (отдельная задача).

## 4. Модель данных

Все таблицы, кроме `organizations`, содержат `org_id` (изоляция данных организаций).

```
organizations(id uuid pk, name, created_at)
users(id, org_id fk, email unique, password_hash, name, role enum[admin, manager, driver], created_at)
vehicles(id, org_id, plate, model, year, created_at)  unique(org_id, plate)
inspections(id, org_id, vehicle_id, driver_id, kind enum[before, after],
            pair_id uuid null,          -- общий id пары до/после
            status enum[draft, uploading, processing, done, failed],
            failure_reason text null, created_at, finished_at)
photos(id, inspection_id, side enum[front, back, left, right], storage_key,
       width, height, quality_score float, quality_flags jsonb, created_at)
       unique(inspection_id, side)
damages(id, org_id, inspection_id, photo_id, type enum[dent, scratch, crack,
        glass_shatter, lamp_broken, tire_flat], zone text null,
        severity enum[low, medium, high] null, confidence float,
        polygon jsonb,                  -- нормализованные координаты 0..1
        source enum[cv, llm], is_new bool null, llm_note text null)
reports(id, org_id, vehicle_id, before_inspection_id, after_inspection_id,
        body jsonb, text, pdf_key null, est_cost_min, est_cost_max, currency, created_at)
chat_messages(id, org_id, user_id, role enum[user, assistant], content, tool_calls jsonb null, created_at)
llm_usage(id, org_id, kind, input_tokens, output_tokens, created_at)   -- контроль расходов
```

Правила:
- Осмотр «после» связывается с осмотром «до» через `pair_id`. Один `pair_id` = ровно один before и один after.
- Полигоны хранятся в нормализованных координатах, чтобы не зависеть от размера картинки.

## 5. API (контракт)

Базовый путь `/api/v1`. Авторизация: cookie `access_token` (httpOnly, JWT). Ошибки:
`{"error": {"code": "...", "message": "..."}}`.

### Авторизация
- `POST /auth/register-org` — создать организацию и первого админа
- `POST /auth/login`, `POST /auth/logout`, `GET /auth/me`
- `POST /users` (admin) — создать менеджера или водителя

### Машины
- `GET /vehicles`, `POST /vehicles`, `GET /vehicles/{id}`, `PATCH /vehicles/{id}`, `DELETE /vehicles/{id}`
- `GET /vehicles/{id}/history` — осмотры и отчёты по машине

### Осмотры
- `POST /inspections` — `{vehicle_id, kind, pair_id?}` → `{id, status:"draft", required_sides:[...]}`
- `POST /inspections/{id}/photos?side=front` — multipart-файл. Ответ:
  `{photo_id, quality:{ok:bool, flags:["blurry"], score:0.62}}`. Если `ok=false`, фронтенд просит переснять.
- `POST /inspections/{id}/finish` — требует 4 фото. Ответ `202 {status:"processing"}`
- `GET /inspections/{id}` — статус, фото (подписанные ссылки), повреждения

Пример ответа `GET /inspections/{id}` (done):
```json
{
  "id": "…", "status": "done", "kind": "after",
  "photos": [{"side": "front", "url": "https://…", "damages": [
    {"id": "…", "type": "scratch", "severity": "medium", "confidence": 0.81,
     "is_new": true, "polygon": [[0.12,0.40],[0.18,0.41],[0.17,0.45]]}
  ]}]
}
```

### Отчёты
- `GET /reports?vehicle_id=&date_from=&date_to=`
- `GET /reports/{id}`, `GET /reports/{id}/pdf`

### Ассистент
- `POST /assistant/chat` — `{message}` → `{answer, sources:[{type, id}]}`

## 6. CV-часть подробно

### 6.1 Данные
- Основной датасет: открытые датасеты повреждений кузова (например, CarDD: порядка 4 тысяч
  изображений, 6 классов: вмятина, царапина, трещина, разбитое стекло, разбитая фара,
  спущенная шина). **Проверь лицензию и условия использования перед публикацией**,
  по описанию датасеты такого рода бывают только для исследований.
- Собственные снимки: 60–100 фото машин друзей и родственников с их согласия, с разными
  повреждениями и условиями (утро, вечер, мокрая машина).
- Разделение: train / val / test = 70 / 15 / 15. **Test не трогать до финальной оценки.**

### 6.2 Обучение (Colab/Kaggle, бесплатный GPU)
1. `prepare_dataset.py`: конвертация разметки в формат YOLO-seg, проверка пустых и битых файлов.
2. Базовая модель: небольшая seg-модель Ultralytics (например, `yolo11n-seg`). Дообучение 50–100 эпох.
3. Оценка: mAP50 и mAP50-95 для масок, precision/recall по каждому классу, матрица ошибок.
4. Разбор ошибок: открой 50 худших предсказаний. Типичные: блики принимаются за царапины,
   грязь за вмятины, тени за повреждения.
5. Улучшение: аугментации (яркость, контраст, масштаб, размытие), класс-веса, более крупная модель
   (`s`), фильтрация шумной разметки.
6. Экспорт весов, фиксация версии и метрик в `docs/model-card.md`.

Ориентир: достичь стабильного результата и **честно** записать метрики, даже если они скромные.
Жюри ценит измеренное качество больше, чем громкие слова.

### 6.3 Проверка качества фото (`quality.py`)
Начальные пороги (подбери на своих фото):
- Размытие: дисперсия Лапласиана < 100 → `blurry`.
- Яркость: средняя < 40 → `too_dark`, > 215 → `too_bright`.
- Разрешение: короткая сторона < 720 px → `low_res`.
- Ракурс и «машина в кадре»: проверка через детектор «car» (стандартная модель) или Vision-LLM.
Результат: `ok`, `flags`, `score`. Если `ok=false`, просим переснять сразу при загрузке.

### 6.4 Детекция (`detector.py`)
Интерфейс: `detect(image) -> list[Detection(type, confidence, polygon_norm)]`.
- Порог уверенности: `>= 0.35` — повреждение; `0.20–0.35` — «сомнительное» (идёт к Vision-LLM).
- Исправлять EXIF-поворот перед инференсом.
- Инференс на CPU: небольшая модель обычно укладывается в 1–3 секунды на фото
  (проверь на своём сервере).

### 6.5 Сравнение «до/после» (`compare.py`)
Для каждой из 4 сторон:
1. Найти ключевые точки (SIFT/ORB) на «до» и «после».
2. Сопоставить (Lowe ratio test ~0.75), посчитать гомографию через RANSAC.
3. Если inliers < 30: `alignment_failed`. Тогда сравнение по зонам кузова с пометкой
   «низкая уверенность», без точной геометрии.
4. Преобразовать маски «до» в систему координат «после».
5. Повреждение «после» считается **старым**, если IoU с любой маской «до» >= 0.30 (порог подбери).
   Иначе **новое** (`is_new = true`).
6. Новое с уверенностью < 0.5 отправляется на подтверждение Vision-LLM или помечается «требует проверки».
7. Повреждения, которые были «до» и пропали «после», игнорируются (но в лог, для отладки).

Ложные срабатывания: блики, капли, грязь. Снижай через требования к качеству фото,
подтверждение LLM и порог уверенности.

### 6.6 Оценка сравнения
Набор `cv/eval/test_pairs/`: минимум 40 пар «до/после» с известной правдой: часть без изменений,
часть с настоящими новыми повреждениями, часть с наклейкой-«царапиной», часть с разной
освещённостью. Метрики: precision/recall по новым повреждениям, доля `alignment_failed`.
Результаты в `cv/eval/results.md`.

## 7. LLM-часть подробно

### 7.1 Интерфейс провайдера (`llm/client.py`)
`generate_structured(schema, messages, images=None) -> pydantic-объект`. Реализация за
интерфейсом, чтобы менять модель и мокать в тестах. Все вызовы логируются в `llm_usage`.

### 7.2 Задачи LLM
1. **Второй эксперт** (только спорные случаи): на вход кроп изображения и описание
   сомнения, на выход `{is_damage, type, severity, reason}`. Лимит вызовов на осмотр (например, 8).
2. **Проверка качества фото:** «видна ли вся сторона машины, какой это ракурс».
3. **Акт осмотра:** схема

```
Report: {
  summary: str,
  vehicle: {plate, model},
  new_damages: [{zone, type, severity, description, photo_side}],
  unchanged_notes: str | null,
  recommendation: "no_action" | "inspect_manually" | "repair_needed",
  disclaimer: str
}
```
   Текст на русском, нейтральный, без обвинения водителя («обнаружено», а не «водитель повредил»).
4. **Оценка стоимости:** сначала таблица `зона × тип × серьёзность → диапазон цен`
   (задаёшь сам в конфиге), LLM лишь корректирует и объясняет. Всегда диапазон и пометка «ориентировочно».

### 7.3 Ассистент менеджера (агент с инструментами)
Инструменты (только чтение):
- `list_vehicles()`
- `get_vehicle_history(vehicle_id)`
- `list_new_damages(date_from, date_to, vehicle_id?)`
- `driver_stats(driver_id, date_from, date_to)`
- `get_report(report_id)`

Правила безопасности:
- `org_id` берётся из сессии пользователя и **никогда** из аргументов LLM.
- Нет произвольного SQL, нет записи и удаления.
- Текст с фото и госномеров считается **недоверенными данными** (возможна инъекция промпта).
- Если данных нет, ассистент говорит «данных нет», а не придумывает.
- Лимит токенов и частоты запросов, ответ со ссылками на источники (id отчётов и осмотров).

### 7.4 Evals для LLM
`llm/evals/`: 20–30 вопросов с ожидаемыми данными на тестовой БД («сколько новых
повреждений у машины X за неделю»). Проверка: правильный инструмент вызван, числа
совпали, при отсутствии данных нет выдумок.

## 8. Фронтенд

Страницы:
- `/login`, `/register` (организация)
- `/vehicles` — таблица, поиск, добавление
- `/vehicles/[id]` — история осмотров, повреждения, отчёты
- `/inspections/new` — **мастер съёмки** на 4 шага (спереди, сзади, слева, справа):
  контур-подсказка поверх камеры, `<input type="file" accept="image/*" capture="environment">`,
  мгновенная проверка качества, повторная съёмка при `ok=false`, сжатие перед отправкой
- `/inspections/[id]` — статус обработки, фото с обводкой (`DamageOverlay` на canvas/SVG)
- `/reports/[id]` — акт, кнопка PDF
- `/assistant` — чат
- `/settings` — пользователи (admin)

Требования: работает с телефона, русский язык, состояния загрузки и ошибки везде,
доступные контрасты. Скриншоты для README делай со всех страниц.

## 9. Безопасность и приватность

- Пароли: argon2 или bcrypt. JWT в httpOnly-cookie, срок короткий. Ограничение попыток входа.
- **Изоляция организаций:** каждый запрос фильтруется по `org_id` из сессии. Тесты на то, что
  пользователь организации A не видит данные B.
- Загрузка файлов: проверка типа по содержимому, размер до 10 МБ, случайные ключи в хранилище,
  выдача по подписанным ссылкам с коротким сроком.
- Секреты только в `.env`, в git нет. `.env.example` без значений.
- CORS только для твоего домена. Rate limit на загрузку, чат и вход.
- Приватность: в демо только тестовые машины и фото. Номера на публичных скриншотах закрывай.
- Лицензии: у Ultralytics YOLO лицензия AGPL (для портфолио допустимо, но укажи в README);
  проверь лицензии датасетов и шрифтов для PDF.
- Перед деплоем: ревью безопасности агентом + твой ручной чек-лист из раздела 13.

## 10. План по неделям и дням

Критерий «готово» (КГ) указан для каждой задачи. Если день не уложился, перенеси в «буфер» недели.
Параллельно с первой недели: 2–3 разговора с представителями парков в неделю (раздел 12).

### Неделя 1. Фундамент
- **Д1. Репозиторий и окружение.** Структура, `AGENTS.md`, Docker Compose (postgres, redis, minio),
  `.env.example`, `README` с запуском. КГ: `docker compose up` поднимает сервисы, `GET /health` отвечает.
- **Д2. БД.** SQLAlchemy-модели из раздела 4, Alembic, первая миграция. КГ: миграция применяется
  и откатывается, есть тест создания записей.
- **Д3. Авторизация и организации.** register-org, login/logout/me, роли, зависимость `current_user`.
  КГ: тесты регистрации, входа, запрета доступа без cookie.
- **Д4. Машины.** CRUD с фильтром по `org_id`. КГ: тест «организация B не видит машины A».
- **Д5. Скелет фронтенда.** Next.js, логин, список машин, API-клиент. КГ: можно войти и увидеть список.
- **Д6. CI и буфер.** GitHub Actions: ruff, pytest, lint фронтенда. КГ: зелёный CI на каждый push.
- **Параллельно (конец недели):** скачать датасет, запустить Colab-ноутбук с первым обучением.

### Неделя 2. Осмотры и загрузка фото
- **Д1. Хранилище.** Сервис MinIO/S3, подписанные ссылки. КГ: загрузка и получение файла в тесте.
- **Д2. Осмотры.** `POST /inspections`, правила пар `before/after`. КГ: нельзя завершить без 4 сторон.
- **Д3. Загрузка фото.** Эндпоинт, валидация файла, `quality.py` (размытие, яркость, разрешение).
  КГ: размытое тестовое фото возвращает `ok=false, flags=["blurry"]`.
- **Д4. Мастер съёмки.** 4 шага, подсказки, повторная съёмка, сжатие. КГ: проходит на телефоне.
- **Д5. Страница осмотра.** Статусы, галерея фото. КГ: после `finish` показывает «обрабатывается».
- **Д6. Тесты и буфер.**

### Неделя 3. CV-модель
- **Д1. Подготовка данных.** `prepare_dataset.py`, проверка разметки, разбиение. КГ: скрипт воспроизводим.
- **Д2. Базовое обучение.** Первый прогон, метрики. КГ: сохранены веса и таблица метрик.
- **Д3. Разбор ошибок.** 50 худших примеров, список причин. КГ: записан в `training/README.md`.
- **Д4. Улучшение.** Аугментации, модель крупнее, чистка данных. КГ: метрики улучшены или объяснено, почему нет.
- **Д5. Модуль инференса.** `detector.py` + тесты на фикстурах. КГ: `detect()` стабильно работает на 20 фото.
- **Д6. Интеграция.** Celery-задача: детектор запускается после `finish`, повреждения сохраняются;
  на фронтенде `DamageOverlay`. КГ: после съёмки видна обводка.

### Неделя 4. До/после
- **Д1. Выравнивание.** SIFT/ORB + RANSAC, тесты на синтетических сдвигах (повернуть/сдвинуть фото
  и проверить восстановление). КГ: тест восстановления проходит.
- **Д2. Сопоставление и `is_new`.** IoU-логика, обработка `alignment_failed`. КГ: юнит-тесты на синтетике.
- **Д3. Тестовый набор.** Собрать минимум 40 пар «до/после» (раздел 6.6). КГ: файлы и разметка в `cv/eval/`.
- **Д4. Оценка.** `run_eval.py`, precision/recall, разбор ошибок. КГ: `results.md` с цифрами.
- **Д5. Vision-LLM.** Второй эксперт для спорных случаев, проверка качества ракурса, лимиты. КГ: тесты с моком LLM.
- **Д6. Буфер.** Подбор порогов по результатам оценки.

### Неделя 5. LLM-слой
- **Д1. Генерация акта.** Схема, промпт, structured output, сохранение в `reports`. КГ: акт по тестовой паре.
- **Д2. PDF.** Страница акта и экспорт PDF (например, через рендер HTML). КГ: PDF открывается, виден русский текст.
- **Д3. Оценка стоимости.** Таблица цен в конфиге + пояснение. КГ: диапазон и пометка «ориентировочно».
- **Д4. Ассистент.** Инструменты, агент, ограничения безопасности. КГ: тест на изоляцию организаций.
- **Д5. Чат во фронтенде.** КГ: вопрос про неделю возвращает данные со ссылками на отчёты.
- **Д6. Evals для LLM** и буфер.

### Неделя 6. Полировка и публикация
- **Д1. Ревью безопасности** (агент + твой чек-лист). Исправления.
- **Д2. Деплой.** VPS, Docker Compose prod, Caddy с HTTPS, бэкапы БД. КГ: сайт открывается по ссылке.
- **Д3. Демо-данные.** Сид-скрипт: организация, машины, пары осмотров. КГ: свежий сервер заполняется одной командой.
- **Д4. Документация.** README (схема, запуск, скриншоты), Model Card, ограничения, лицензии.
- **Д5. Демо-видео и слайды.** Видео 1–2 минуты, питч 3–5 минут.
- **Д6. Репетиция.** Прогон демо 10 раз, ответы на вопросы, резервный план.

### Линия отсечения (если не успеваешь)
Убирай в таком порядке: оценка стоимости → чат-ассистент → PDF → роли (оставить одну) →
Vision-LLM как второй эксперт. **Не убирай:** загрузку 4 фото, детекцию, сравнение до/после,
акт, деплой, README.

## 14. Демо и питч

### 14.1 Сценарий демо (4 минуты)
1. (20 с) Проблема одной фразой и цифра из твоих разговоров.
2. (90 с) **Живая съёмка:** человек из зала фотографирует машину «до», вы ставите наклейку-царапину,
   фотографируете «после».
3. (30 с) Система находит новое повреждение, показывает обводку и акт.
4. (30 с) Менеджерский кабинет: история машины и вопрос ассистенту.
5. (30 с) Как это устроено: слои ИИ и метрики качества.
6. (20 с) Модель дохода и что дальше.
**Резервный план:** заранее подготовленные пары фото и видеозапись демо на случай проблем с интернетом.

### 14.2 Слайды (8 штук)
Проблема → решение → демо → как работает (ИИ-слои) → доказательства спроса → бизнес-модель
(например, подписка за машину в месяц, цифры из интервью) → конкуренты и отличие → что нужно дальше.

### 14.3 Вопросы, к которым подготовиться
- «Чем отличаетесь от глобальных сервисов (Ravin, Tractable, Verdict Capture и др.)?»
  (локальный язык, цена, простота для малых парков, поддержка).
- «А если ИИ ошибётся?» (показываешь уверенность, ручную проверку и метрики).
- «Что с приватностью фото?» (хранение, доступ по организациям, удаление).
- «Как зарабатываете?» (подписка + цифры).
- «Что, если банки/парки сделают сами?» (скорость внедрения, готовый продукт, данные).

## 15. Риски и запасные решения

| Риск | Что делать |
|---|---|
| Модель плохо работает на реальных фото | Добавить свои фото, аугментации, поднять порог, показывать «требует проверки» |
| Выравнивание не срабатывает | Сравнение по зонам с пониженной уверенностью, требовать фото с одной точки |
| Нет GPU | Colab/Kaggle для обучения, на сервере только CPU-инференс небольшой модели |
| LLM дорого или лимит | Вызывать только для спорных случаев, кэшировать, мок в тестах |
| Не успеваешь | Линия отсечения из раздела 10 |
| Нет клиентов для разговоров | Парки через знакомых, группы владельцев такси, объявления аренды; 5 разговоров лучше нуля |
| Проблемы с интернетом на показе | Видео и заготовленные данные локально |

## 17. Глоссарий
- **mAP50:** метрика качества детекции при пороге пересечения 0.5.
- **IoU:** доля пересечения двух масок (пересечение / объединение).
- **Гомография:** преобразование, совмещающее два снимка одной плоскости.
- **RANSAC:** метод, устойчивый к ошибочным совпадениям ключевых точек.
- **Structured output:** ответ LLM строго по заданной схеме.
- **Инъекция промпта:** попытка заставить LLM выполнить чужую инструкцию из «данных».
